# Full PT-BR skill-tooltip reconstruction across the generator, OCR DLL, and overlay (v1)

Bronco previously showed only a translated skill *name* on screen; this change reconstructs the entire tooltip. The Python generator now emits a structured `skills_tooltips.json` (name/type/description/flags/categories plus one normalized entry per fact) and a companion `fact_labels.json`; the OCR DLL loads that dataset, matches an OCR line to an English skill name using the exact same normalization and word-boundary rules as the existing dictionary, and emits the whole tooltip as ordered, pre-formatted PT-BR lines tagged with a `lineKind`; the overlay renders those lines by kind so the panel reads like a clean tooltip instead of raw OCR. The path is additive — a missing dataset degrades to the old name-only behavior rather than failing engine init.

Watch for: the extended `bronco_ocr_initialize` signature must stay in lockstep across the header, the DLL, the loader typedef, and the caller (confirmed consistent here); the `resultStorage` reserve-then-emit contract is what keeps the returned `c_str()` pointers alive and must not regress (confirmed intact); and the reconstructed "effects" carry labels/durations/stacks but not absolute damage numbers, which GW2 does not ship in static data (confirmed — relevant to the stated goal). No blocking issues found.

**Verdict**: APPROVED

## High-level view

The design keeps the tooltip store parallel to the existing dictionary: `SkillTooltipStore` keys on `Dictionary::normalize(name_en)` and reuses `Dictionary::containsOnWordBoundary` (both promoted to public statics) so tooltip matching can never diverge from the name matcher that already ships. Loading is decoupled from `Translator::initialize` and is best-effort, so the feature is genuinely additive.

The cross-DLL contract grew one parameter: `skillDataPath` is threaded through `ocr_api.h/.cpp`, `ocr_loader.h/.cpp`, and `pipeline.cpp`, inserted in the same position everywhere and reflected in the function-pointer typedef. The C ABI surface (`BroncoOcrResult`) gained an `int lineKind` and the result cap moved 64→96 to fit a multi-line tooltip.

String-lifetime marshalling is the load-bearing invariant. `process_frame` clears and reserves `resultStorage` to `BRONCO_OCR_MAX_RESULTS` before the emit loop, and every emitted line is gated by a `count >= BRONCO_OCR_MAX_RESULTS` check, so the vector never reallocates and the `c_str()` pointers handed back to the caller stay valid for the whole call.

The fact formatter handles each known GW2 fact kind and falls through to a generic "label + first present numeric value" for unknown kinds, so a schema the tool has not seen still renders something rather than crashing or vanishing. The visible "effect value/frequency" is limited to what static data contains — hit counts, durations, stacks, percentages — never the stat-scaled damage number, which is inherent to GW2 and worth setting expectations around.

The overlay renders matched lines only, in emission order, de-duplicated on `(lineKind, text)` and capped at 40, styling each kind differently. Skill `name`/`type`/`description` are translated through the same `translate_label` path built for short fact labels, which is fine for labels and types but means long descriptions rely entirely on the Argos fallback. Two unrelated task-tracking JSON edits ride along in the diff.

### Tooltip matching shares the dictionary's normalization instead of forking it

`Dictionary::normalize` and `Dictionary::containsOnWordBoundary` were moved from private to public static, and `SkillTooltipStore` builds its keys with `normalize(name_en)` and runs the same two-pass lookup — exact normalized match, then longest-key word-boundary "contains" using the same substantial-key thresholds (multi-word ≥ 6, single word ≥ 8). Because both matchers consume identical primitives, a line matched by the name path and a line matched by the tooltip path cannot silently drift apart as the normalization evolves. The header change is a pure visibility move; no member layout or behavior of `Dictionary` otherwise changed.

Lookup returns the tooltip independent of the dictionary's translated value, so a full tooltip is produced even for a skill whose name-only dictionary entry is missing — the tooltip's own `name` (falling back to `name_en`) drives the header.

### Cross-DLL signature growth is consistent, and load is best-effort

```
pipeline.cpp        ocr_loader.cpp         ocr_api.cpp
config.skillDataPath()  ── initialize(...) ── bronco_ocr_initialize(
   │                        skillDataPath)      ..., skillDataPath, ...)
   └────────────── same position: after locale, before confidenceThreshold ─┘
```

`skillDataPath` is inserted after `locale` and before `confidenceThreshold` in every declaration and call site, and `PFN_Initialize` gained the matching fifth `const char*`. `bronco_ocr_initialize` guards `if (skillDataPath)` before loading, so an older caller passing null does not crash, and a failed/absent dataset logs and leaves the name-only path active rather than failing `initialize` — a fail-open posture appropriate for an additive feature.

### resultStorage reserve keeps returned pointers alive

The refactor from one push-per-line into an `emitLine` lambda preserves the invariant that matters across the C ABI: `outResults[i].originalText/translatedText` point into `std::string`s owned by `handle->resultStorage`. Before the emit loop the vector is `clear()`ed and `reserve(BRONCO_OCR_MAX_RESULTS)`d; `emitLine` refuses to push once `count >= BRONCO_OCR_MAX_RESULTS`. Because emitted lines and vector elements advance in lockstep under the same cap, the vector never exceeds its reserved capacity, so no reallocation occurs mid-call and every previously returned `c_str()` stays valid. A single matched skill can emit up to `1 + 1 + 1 + notes + facts` lines, and the raised 64→96 cap plus the per-line guard means a large tooltip is truncated cleanly rather than overflowing the caller's array.

### Fact formatting degrades gracefully on unknown kinds

`formatFact` dispatches on the verbatim API `type`: Damage/Heal as label + `(xN)` when hits > 1, Duration/Time as `label: N segundo(s)`, Recharge as `label: N s`, Buff/PrefixedBuff from the translated `status` plus stack count, duration, description, and a bracketed nested prefix status. The load-bearing property is the terminal fallback: an unrecognized or empty `type` (the comment cites `BuffArray`) still emits the translated label plus the first present numeric field, so an unseen schema variant produces a line instead of disappearing or throwing.

The gap relative to the stated goal — "o valor de seu efeito" — is that Damage facts have no absolute number to show; GW2 computes displayed damage from character stats at runtime and ships only `hit_count`/`dmg_multiplier` statically. Frequency (hit count, apply count, duration) is represented; the final damage figure structurally cannot be. This is a data-source limitation, not a defect, but it should be stated so users do not expect a damage number.

### Overlay renders structured lines in emission order, and the prior C2065 is not reintroduced

`render()` collects only `entry.matched` lines with non-empty text, de-duplicates on `lineKind + "\x1f" + translated` (so the same text at a different kind survives but repeated frames collapse), caps at 40, and switches on kind for styling. `TranslatedEntry` gained `int lineKind` mirroring the C ABI field, and `pipeline.cpp` copies `result.lineKind` into it, so the hint flows end to end without re-parsing strings in the renderer.

The prior C2065 build failure (a drag-modifier variable used outside its block) is not reintroduced: `dragModifierHeld` remains declared at function scope (line 287) and is read at both the window-flags site and the trailing `g_captureMouse.store(dragModifierHeld)`; the diff only touches the panel-body block between them, and `<unordered_set>` is already included for the de-dup set.
